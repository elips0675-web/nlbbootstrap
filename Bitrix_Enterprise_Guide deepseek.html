1С-Битрикс: Enterprise-руководство

Консолидированное руководство по архитектуре, безопасности, оптимизации и качеству кода на платформе 1С-Битрикс: Управление сайтом. Сведено из трёх источников: Bitrix_Enterprise_Guide.html, bitrix_architecture (2).html и Bitrix_Enterprise_Guide (1).md.

Назначение документа Руководство ориентировано на enterprise-стандарт разработки: D7 ORM, контейнеризация, CI/CD, статический анализ, автотесты, централизованное логирование. Оно описывает целевое состояние, а не текущее состояние какого-либо проекта.

Что есть в проекте, чего нет

Руководство описывает зрелый enterprise-подход. Если применять его к типовому «лёгкому» шаблону (например, к шаблону сайта библиотеки nlb_bootstrap), нужно понимать разрыв между целевым и фактическим состоянием.

Чего нет в самих руководствах Руководства не привязаны к конкретному проекту: нет исходного кода, скриншотов, Git-истории, логов, результатов Lighthouse/PSI, конфигов сервера. Все выводы о поведении — гипотезы, требующие запуска на живом ядре.

1. Архитектура и качество кода

С точки зрения современной программной инженерии, «1С-Битрикс: Управление сайтом» — это тяжёлое монолитное легаси, но с уникальным коммерческим статусом в СНГ-сегменте.

Критикуемые стороны

  • Два ядра одновременно: процедурное старое ядро и ООП D7 уживаются из-за требований обратной совместимости.
  • Отсутствие жёстких рамок: платформа не навязывает DI и Middleware — руки плохим практикам развязаны.
  • Смешанная шаблонизация: нет компилируемого шаблонизатора (Twig / Blade) — обилие PHP в вёрстке.

Сильные инженерные решения

  • Компонентный подход: бизнес-логика и представление разделены, обновления ядра не ломаются.
  • Современная ORM в D7: декларативное описание схем, встроенное кеширование.
  • Преемственность: проекты 10-летней давности обновляются до актуальных сборок.

3. Архитектурные стандарты и файловая структура

Все кастомные наработки должны быть изолированы в /local/. Изменения в /bitrix/ строго запрещены.

  • /local/templates/ — шаблоны сайтов.
  • /local/components/ — кастомные компоненты (ООП-подход, class.php).
  • /local/modules/ — собственные модули бизнес-логики.
  • /local/php_interface/init.php — только подключение автозагрузчиков и конфигов. Логика выносится в модули.

4. Модульность ядра проекта

Вся уникальная бизнес-логика крупного проекта (интеграции с ERP, программа лояльности) пишется в виде собственных модулей, регистрируемых в /local/modules/vendor.project/. Подключение — через стандартный Loader::includeModule.

5. Современный API D7 и ORM

Старые глобальные методы (CIBlockElement::GetList) не рекомендуются. Используется типизированный ORM-подход D7:

use Bitrix\Main\Loader;
use Bitrix\Iblock\Elements\ElementCatalogTable;

Loader::includeModule('iblock');

$elements = ElementCatalogTable::getList([
    'select' => ['ID', 'NAME', 'PRICE_VALUE' => 'PRICE.PRICE'],
    'filter' => ['=ACTIVE' => 'Y'],
    'runtime' => [
        'PRICE' => [
            'data_type' => '\Bitrix\Catalog\PriceTable',
            'reference' => ['=this.ID' => 'ref.PRODUCT_ID'],
            'join_type' => 'left'
        ]
    ],
    'cache' => ['ttl' => 3600]
])->fetchAll();

6. Highload-блоки и Big Data

Стандартные инфоблоки используют схему EAV (Entity-Attribute-Value). При десятках свойств СУБД выполняет множество JOIN, что резко снижает производительность на больших массивах. Для каталогов с миллионами позиций и логов используются Highload-блоки — плоские реляционные таблицы с прямой индексацией.

use Bitrix\Main\Loader;
use Bitrix\Highloadblock\HighloadBlockTable;

Loader::includeModule("highloadblock");

$hlblock = HighloadBlockTable::getById(2)->fetch();
$entity = HighloadBlockTable::compileEntity($hlblock);
$entityDataClass = $entity->getDataClass();

$rsData = $entityDataClass::getList([
    "select" => ["ID", "UF_NAME", "UF_CODE"],
    "filter" => ["=UF_ACTIVE" => 1],
    "order"  => ["ID" => "DESC"],
    "limit"  => 20,
    "cache"  => ["ttl" => 3600]
]);

while ($arItem = $rsData->fetch()) {
    // Безопасная обработка
}
Когда Highload не нужен Для каталогов с десятками–сотнями элементов стандартные инфоблоки работают нормально. Highload оправдан при миллионах записей или логах. Не путайте «много полей» с «много записей».

7. Миграции БД и CI/CD

Главная проблема Битрикса в командной разработке — хранение настроек (структуры инфоблоков, свойств, модулей) в базе данных, а не в коде. Решение — система миграций sprint.migration.

Git-Flow пайплайн

  1. Разработчик создаёт сущность локально в админке.
  2. Генерирует файл миграции через CLI: php migrate.php add.
  3. Пушит код и файл миграции в Git.
  4. Пайплайн (GitLab CI / GitHub Actions) собирает артефакты, делает деплой через rsync и автоматически накатывает изменения в БД.
# Деплой на целевом сервере
cd /var/www/bitrix_project/
git pull origin main

## Проверка статуса и автоматический накат миграций без веб-интерфейса
php local/php_interface/migrate.php up --all
Альтернатива Если в проекте уже есть свои идемпотентные миграции на API Битрикса (как в nlb_bootstrap — 12 шагов db/migrations/001–012.php), sprint.migration может дублировать функциональность. Выбор зависит от зрелости проекта и команды.

8. Безопасность и валидация входящих данных

Все входящие запросы проходят фильтрацию через объект Context. Прямое использование $_POST / $_GET запрещено.

use Bitrix\Main\Application;

$request = Application::getInstance()->getContext()->getRequest();
$userId = $request->getPost('user_id');

$userId = intval($userId);
if ($userId <= 0) {
    throw new \InvalidArgumentException('Некорректный ID пользователя');
}

9. Чек-лист: комплексная безопасность

  • Проактивный фильтр (WAF): включить встроенный экран защиты Битрикса.
  • Защита сессий: перенос из файлов в Redis с включённой сменой идентификаторов.
  • Блокировка PHP в /upload/: запрет выполнения скриптов в пользовательских директориях.
  • 2FA для админов: двухфакторная аутентификация для всех административных учёток.

10. Безопасность Enterprise-уровня

Обязательное включение модуля «Проактивная защита». Конфигурация веб-серверов (Nginx, PHP-FPM) должна исключать выполнение PHP в пользовательских директориях загрузки (например, в /upload/).

11. Оптимизация и стратегии кэширования

Кастомный код со сложными вычислениями или запросами к БД оборачивается в управляемый или неуправляемый кэш:

$cache = \Bitrix\Main\Data\Cache::createInstance();
$cacheId = 'custom_user_data_' . $userId;
$cachePath = '/project/user_data/';

if ($cache->initCache(3600, $cacheId, $cachePath)) {
    $result = $cache->getVars();
} elseif ($cache->startDataCache()) {
    $result = ComplexCalculationMethod($userId);

    // Тегированный кэш для инвалидации при изменении данных
    $taggedCache = \Bitrix\Main\Application::getInstance()->getTaggedCache();
    $taggedCache->startTagCache($cachePath);
    $taggedCache->registerTag('user_profile_' . $userId);
    $taggedCache->endTagCache();

    $cache->endDataCache($result);
}

12. Чек-лист: оптимизация быстродействия

  • Конвертация СУБД в InnoDB: перевод всех таблиц с MyISAM на InnoDB с корректным innodb_buffer_pool_size.
  • Кэширование: автокэш компонентов + перенос файлового кэша на Redis / Memcached.
  • CSS/JS: объединение, сжатие, минификация в настройках Главного модуля.
  • Композитный сайт: разделение страницы на статическую (из кэша) и динамическую (асинхронную) зоны.

13. Разработка быстрых и безопасных шаблонов

Золотое правило: в template.php запрещены SQL-запросы и GetList. Вся подготовка данных — в контроллере компонента или в result_modifier.php.

Защита от XSS (экранирование вывода)

<?// Небезопасно ?>
<div class="desc"><?=$arItem["PREVIEW_TEXT"]?></div>

<?// Безопасно через D7 API ?>
<div class="desc"><?=\Bitrix\Main\Text\HtmlFilter::encode($arItem["PREVIEW_TEXT"])?></div>

<?// Либо классический хелпер ?>
<div class="title"><?=htmlspecialcharsbx($arItem["NAME"])?></div>

Динамическая зона в Композите

<div class="basket-block">
<?
$frame = $this->createFrame()->begin();
?>
Товаров в корзине: <?=$arResult["BASKET_COUNT"]?>
<?
$frame->beginStub();
?>
Загрузка корзины...
<? $frame->end(); ?>
</div>

14. Перенос ИИ-вёрстки (DeepSeek, Qwen) на Битрикс

Интеграция сырого HTML/CSS/JS от нейросети требует декомпозиции и приведения к компонентной архитектуре CMS.

Алгоритм «натяжки»

Шаг 1. Разрезка шаблона. Верхняя неизменяемая часть index.html → /local/templates/main/header.php. Нижняя → footer.php.

Шаг 2. Подключение системных методов. В начале header.php — пролог ядра, панель админа, метатеги:

<?if(!defined("B_PROLOG_INCLUDED") || B_PROLOG_INCLUDED!==true)die();?>
<!DOCTYPE html>
<html>
<head>
    <?$APPLICATION->ShowHead();?>
    <title><?$APPLICATION->ShowTitle();?></title>
</head>
<body>
<div id="panel"><?$APPLICATION->ShowPanel();?></div>

Шаг 3. Регистрация CSS и JS через Менеджер Ассетов. Замените статические <link> и <script> на системные вызовы D7:

<?
use Bitrix\Main\Page\Asset;

Asset::getInstance()->addCss(SITE_TEMPLATE_PATH . "/css/deepseek-style.css");
Asset::getInstance()->addJs(SITE_TEMPLATE_PATH . "/js/deepseek-core.js");
?>

Шаг 4. Декомпозиция в компоненты. Блоки с динамикой (карточки, слайдеры, отзывы) вырезаются в изолированные шаблоны компонентов (например, bitrix:news.list). Статические тексты ИИ внутри циклов заменяются на безопасный вывод из $arResult / $arItem.

15. Управление асинхронностью и AJAX

AJAX-интерфейсы опираются на стандартные контроллеры Битрикса, возвращающие JSON, а не на отдельные PHP-файлы в корне сайта. Это гарантирует сессионные проверки и безопасность.

16. Проектирование REST API на базе D7

Битрикс часто выступает Headless-платформой для внешних JS-фронтендов (Vue / React) и мобильных приложений.

use Bitrix\Main\Engine\Controller;

class OrderApiController extends Controller
{
    public function configureActions()
    {
        return [
            'getDetails' => [
                'prefilters' => [
                    new \Bitrix\Main\Engine\ActionFilter\Authentication(),
                    new \Bitrix\Main\Engine\ActionFilter\HttpMethod(['GET'])
                ]
            ]
        ];
    }

    public function getDetailsAction($orderId)
    {
        return [
            'status' => 'success',
            'data' => [
                'orderId' => (int)$orderId,
                'amount' => 15400.00
            ]
        ];
    }
}

Все эндпоинты документируются через OpenAPI / Swagger.

17. Оптимальное серверное окружение

Для максимальной скорости рекомендуется отказаться от Apache + Nginx в пользу чистого стека Nginx + PHP-FPM.

RAM-кэш и сессии на Redis в bitrix/.settings.php

<?php
return [
    'cache' => [
        'value' => [
            'type' => [
                'class_name' => '\Bitrix\Main\Data\CacheEngineRedis',
                'extension' => 'redis'
            ],
            'redis' => ['host' => '127.0.0.1', 'port' => 6379],
            'sid' => 'bitrix_prod_site'
        ],
        'readonly' => false,
    ],
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'redis',
                    'host' => '127.0.0.1',
                    'port' => 6379,
                ]
            ]
        ],
        'readonly' => false,
    ]
];

18. Локальное окружение разработки (Docker)

Enterprise-стандарт требует изоляции окружения каждого разработчика. Вместо тяжёлой BitrixVM — Docker-контейнеризация.

  • Контейнеры: nginx, php-fpm, percona/mysql (или MariaDB), redis, mailhog.
  • Перехват почты: Mailhog перехватывает все SMTP-вызовы PHP, исключая отправку тестовых писем реальным клиентам.
  • Изоляция конфигурации: доступы, ключи API и флаги отладки — в .env. У каждого окружения (Dev, QA, Stage, Production) свои параметры.

19. Статический анализ и линтеры

Без автоматического контроля код быстро превращается в хаос. В CI/CD встраиваются:

  • PHP_CodeSniffer: проверка оформления кода на соответствие PSR-12 и правилам именования Битрикса.
  • PHPStan / Psalm: статические анализаторы уровня 1–5 — ловят Null-объекты, неверные типы, ошибки ORM без запуска кода.
  • Git Hooks (Husky / GrumPHP): проверки запускаются автоматически при коммите. Ошибки — коммит блокируется.

20. Автоматизированное тестирование

Битрикс сложен для тестирования из-за глобальных переменных ($APPLICATION, $USER, $DB), но для Enterprise это обязательный шаг.

  • Юнит-тесты (PHPUnit): покрытие чистых функций и сервисов (калькуляторы скидок, логика лояльности). Изоляция от глобальных объектов — через DI и Service Locator D7.
  • Интеграционные тесты: проверка работы кода с реальной тестовой БД — создание сущностей через ORM, транзакции, обработчики событий.
  • E2E (Codeception / Cypress): сквозные сценарии — «зашёл → добавил в корзину → применил купон → оформил заказ».

21. Мониторинг и Observability

Enterprise-система должна сообщать о сбоях раньше, чем клиент напишет в поддержку.

  • Централизованное логирование (PSR-3): отказ от разрозненных локальных логов. Библиотека Monolog + ELK-стек или Grafana Loki.
  • Трекинг ошибок (Sentry): SDK в init.php — любое необработанное исключение отправляет алерт со стеком в мессенджеры команды.
  • APM (New Relic / OpenTelemetry): мониторинг производительности «под нагрузкой» — медленные SQL-запросы и узкие места компонентов на живом трафике.

22. Встроенные инструменты аудита Битрикса

В системе отсутствуют публичные визуальные компоненты замера скорости или сканирования безопасности: вывод подобных данных наружу создаёт уязвимость. Анализ — только через административную панель.

🏆 Монитор качества (Сервисы → Монитор качества)

Автоматический чек-лист из 65 обязательных тестов: хостинг, безопасность, производительность кода, корректность интеграции с платформой. Используется перед сдачей проекта в эксплуатацию.

Монитор производительности

  • Панель производительности: стресс-тест CPU, диска и СУБД с эталонными баллами.
  • Скорость сайта (RUM): анализ реального пользовательского опыта загрузки.

Проактивная защита

  • Сканер безопасности: статический анализ кода на XSS и SQL-инъекции.
  • Контроль целостности: проверка ядра на модификацию вредоносным ПО.
Что не покрыто руководствами Руководства сфокусированы на архитектуре и инфраструктуре. За рамками остались: PWA (манифест, service worker, офлайн-заглушка), SEO (canonical, OG, Twitter, JSON-LD, sitemap, robots), формы заявок с CAPTCHA и согласием, доступность (aria, focus-trap, contrast), адаптивные изображения (WebP/AVIF, srcset). Для сайтов библиотек и культурных учреждений эти разделы критичны — они должны быть добавлены отдельно.
