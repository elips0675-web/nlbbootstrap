3. Чего не учёл исходный черновик

Черновик «Выбор CMS: Bootstrap 5, PageSpeed 100, удобные поля» отвечает на вопрос «какая CMS даёт три свойства» — и отвечает добросовестно. Но критерии он применяет к маркетинговому сайту, а здесь шаблон с заявками, бронью с слотами, поиском, push и админской обработкой заявок.

Поправка 1. «Перенос — 1–2 дня на CSS» верно не для всего

Оценка справедлива для шести контентных инфоблоков и 39 полей каталога (news 4, events 8, collections 3, books 9, services 11, printing 4). Остальные 35 полей — это requests (9), bookings (14), orders (12): они живут не полями, а валидацией, письмами, транзакциями и статусами. Плюс 2 300+ строк nlb_forms.php, nlb_search.php, nlb_push.php — это код, а не разметка.

Поправка 2. «Битрикс: Bootstrap 5 — 4/5, PageSpeed — 3/5» — это про дефолтный Битрикс

В этом шаблоне Bootstrap 5.3, урезанный bootstrap.min.css 59,9 КБ (tools/purge-css.mjs), CSS встроен в документ и сжат, CSS-запросов ноль. Performance 100 достигнут и на статике, и на проде. Оценка 3/5 к этому шаблону не относится — она про установку «из коробки».

Главный критерий, которого нет в черновике: не «какая CMS легче», а «какая CMS выдержит 74 поля и три серверных сценария, не заставив переписать формы, брони и поиск». Лёгкость ядра здесь вторична: TTFB решается кешем HTML, а потеря функционала — только кодом.

4. Рейтинг CMS именно под nlb_bootstrap

Место 1 · если цель — сохранить функционал

1С-Битрикс (остаётся)

Единственная незакрытая цифра — TTFB 1,9 с на стенде, и это кеш HTML, а не CMS. Смена CMS здесь = переписать 2 300+ строк логики.

  • 0 дней на перенос, 74 поля и формы уже есть;
  • 100/100/100/100 уже на статике и на проде;
  • минус: TTFB и «UI 2000-х» в админке — лечится кешем, не переездом.
Место 2 · если переезд обязателен

October CMS + Tailor

Лучший вариант под этот случай: Tailor-поля ложатся на 74 свойства, а Laravel даёт настоящие транзакции — P1-20 (гонка слота) закрывается архитектурно, а не костылём.

  • PHP + MySQL совпадают с текущим хостингом;
  • есть стартеры на Bootstrap 5;
  • self-host без подписки (лицензию и цену проверить у вендора);
  • минус: 2–4 недели на формы, брони, поиск, push, админку.
Место 3 · если заявки уезжают в отдельный сервис

Statamic

Blueprints — действительно самые удобные поля из списка, TTFB 20–50 мс. Но Statamic даёт контент, а не приложение: бронь, поиск и push придётся писать на Laravel отдельно.

  • + поля и кеш из коробки, чистый PHP-стек;
  • − платная лицензия для продакшена, меньше специалистов;
  • − без отдельного кода нет ни заявок, ни слотов.
Не рекомендуется под этот шаблон

WordPress + ACF

Привычно и дёшево по фрилансерам, но худший вариант именно здесь: 100 держится на дисциплине плагинов, запись через Amelia/Bookly приносит чужую разметку и JS — это и рушит 100.

  • подход «CSS внутри <style> без запросов» живёт только в полностью своей теме;
  • серверную валидацию, поиск и push всё равно писать самому;
  • итог: шаблон переписывается целиком, но с плагинной зависимостью.
Не для этой задачи

Grav CMS

«100 почти автоматически» — правда, но flat-file без транзакций: бронь слота на файлах это ручные блокировки, а каталог книг на тысячах записей начинает отставать от БД.

  • + быстрый старт, понятная файловая структура;
  • − Flex Objects слабее iBlock-свойств;
  • − P1-20 в Grav не решается штатно.
Не замена CMS, а статический слой

Astro + Decap

Хорошая новость: этот слой у вас уже есть — preview/ это 110 готовых страниц, Vercel их деплоит, 100/100/100/100. Но формы, брони, поиск и push останутся без бэкенда.

  • + абсолютная скорость и уже работающий деплой;
  • − контент правится через Git, нужен разработчик для CI/CD;
  • − как «CMS для шаблона» не годится.

Contao, Vvveb, MODX под эту задачу не рассматриваю: либо нет экосистемы в RU/BY, либо молодой проект для продакшена, либо вся гибкость уходит в настройку без выигрыша по трём критериям.

7. Итог и три сценария

Сценарий A. «Нужен функционал и минимум риска»

Битрикс остаётся. Добиваем TTFB кешем готового HTML на стенде, закрываем P1-20 (атомарная бронь) и P0-4/P0-5 (письма и рассылка). Ни одна строка логики не переписывается.

Сценарий B. «Нужна универсальная CMS вместо Битрикса»

October CMS + Tailor. Переносится разметка и 74 поля, формы, брони с транзакциями, поиск и push пишутся на Laravel. Второй номер — Statamic, если сайт живёт как каталог, а заявки уезжают в отдельный сервис.

Сценарий C. «Нужна максимальная скорость и не жалко CI/CD»

Статика уже есть: preview/ на Vercel, 100/100/100/100. Дальше это не «CMS для шаблона», а разделение: статический фронт + API для заявок и брони (Node/Laravel/serverless). Дороже по разработке, дешевле по эксплуатации.

Короткая рекомендация. Под три исходных критерия (Bootstrap 5, PageSpeed 100, удобные поля) черновик верно называет WordPress + ACF. Под этот шаблон — нет: у вас не сайт, а приложение с заявками, бронью и поиском. Поэтому: остаёмся на Битриксе, если нужен функционал; October CMS (Tailor), если переезд обязателен; WordPress + ACF — только когда приоритет «дёшево найти фрилансера» и функционал всё равно выносится из CMS.
