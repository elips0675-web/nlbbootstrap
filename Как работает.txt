================================================================
1. ЧТО СЕЙЧАС ЗАПУЩЕНО
================================================================

Это не сайт, а статическая копия. Поднят python -m http.server на порту 8791,
он раздаёт папку preview/ — обычные .html, собранные скриптом
tools/build-preview-pages.php. PHP, MySQL и ядра Битрикса там нет вообще.

Проверено на живом сервере:

    POST http://127.0.0.1:8791/books/  ->  501 Not Implemented

То есть кнопки «Заказать» / «Забронировать» сейчас работают только как вёрстка:

    Где                Куда ведёт кнопка                 Что при отправке
    ------------------------------------------------------------------------
    /services/<код>/   якорь #booking, форма на странице  script.js:1370-1378
                                                          проверяет required
                                                          в браузере, дальше
                                                          POST -> 501
    /books/<код>/      якорь #order, форма на странице    то же, POST на
                                                          ../../books/ -> 501
    /printing/<код>/   ../../feedback/ (общая форма       отдельного заказа
                       обращений)                         для печати нет

JS в превью умеет только косметику:
- подставить тариф/цену в скрытые поля (preview/script.js:1405-1418);
- заблокировать занятые часы по data-nlb-slots (preview/script.js:1426-1473);
- собрать название заявки.
Сохранять некуда — базы нет.

================================================================
2. КАК ЭТО БУДЕТ РАБОТАТЬ НА БИТРИКСЕ
================================================================

Через штатный компонент bitrix:iblock.element.add.form (бесплатный, входит
в «Старт»; модуль «Веб-формы» и CRM-формы не нужны). Свой шаблон:
local/templates/nlb_bootstrap/components/bitrix/iblock.element.add.form/
bootstrap/template.php

Схема: заявка = элемент инфоблока, письмо — только уведомление поверх записи.

    Форма           Где                          Инфоблок    NLB_FORM
    ------------------------------------------------------------------
    Обращение       /feedback/ + модалка в       requests    request
                    подвале
    Бронь услуги    /services/<код>/#booking     bookings    booking
    Заказ сувенира  /books/<код>/#order          orders      order

Инфоблоки описаны в db/config/iblocks.php:499-582 (bookings)
и :584-656 (orders), создаются миграцией db/migrations/008_requests.php,
тип nlb_content.

ПУТЬ ОДНОГО КЛИКА

1. services/detail.php:80-98 (и books/detail.php:91-110) подключают
   компонент с NLB_FORM => 'booking' / 'order'.
2. nlb_form_render() (local/php_interface/include/nlb_forms.php:602-830)
   рисует форму: bitrix_sessid_post(), CAPTCHA (USE_CAPTCHA=Y), скрытые
   PROPERTY[<ID>][0] — SERVICE / SERVICE_CODE / TARIFF / PRICE либо
   ITEM / ARTICLE / PRICE.
3. POST идёт на тот же URL, компонент делает CIBlockElement::Add
   в bookings / orders.
4. OnBeforeIBlockElementAdd -> nlb_forms_before_add()
   (nlb_forms.php:878-937): согласие на обработку ПД, дата не в прошлом,
   слот не занят — на сервере, независимо от JS.
5. OnAfterIBlockElementAdd -> nlb_forms_after_add() (nlb_forms.php:1010): письмо
   NLB_NEW_REQUEST через CEvent::Send; в теле тип, имя, телефон, услуга,
   дата, время, товар и ссылка на элемент в админке.
6. Редирект на ?sent=1#order (или #booking), вместо формы — «Спасибо!
   Заказ сохранён…» (components/bitrix/iblock.element.add.form/bootstrap/template.php:52).
7. Менеджер видит заявку в админке: «Контент -> Заказы сувениров» /
   «Заявки на услуги». Статусы — свойство-список:
      заказы: new -> processing -> done / cancelled;
      брони:  new -> confirmed / cancelled.

БРОНЬ — единственная «умная» форма:
- слоты 10:00–21:00 (nlb_form_time_options());
- занятые берутся из уже созданных элементов (nlb_form_slots(), nlb_forms.php:435-488)
  и приходят в data-nlb-slots;
- отменённая бронь слот освобождает;
- двойная защита: JS гасит <option> + серверная nlb_form_slot_taken()
  (nlb_forms.php:490-524).

ПОЧТА: тип события и шаблон создаёт 008_requests.php:120-205. После
установки в админке надо прописать реальный EMAIL_TO вместо демо
info@example.by — docs/bitrix-integration.md:344-347.

ПРАВА: у инфоблоков заявок группа 2 («Все пользователи») имеет W, иначе
анонимная форма не создаст элемент; поисковый индекс выключен, чтобы ПД
не попадали в поиск (iblocks.php:453-455, :507-509, :592-594).

================================================================
3. ЧЕГО В ЭТОМ РЕШЕНИИ НЕТ
================================================================

- Нет корзины и онлайн-оплаты. «Заказать» = заявка «перезвоните и
  подтвердите»; оплата и наличие — вручную. Для оплаты нужен отдельный
  модуль (интернет-магазин / платёжная система), это другой объём работ.
- Нет личного кабинета с историей заявок — ELEMENT_ASSOC=NONE,
  MAX_USER_ENTRIES=0, всё анонимно.
- Нет проверки склада — свойство AVAILABLE у товара просто текст,
  остаток не списывается.
- Печать (/printing/) не имеет своего инфоблока заказов: кнопка уводит
  в общую форму обращений requests. Если нужен учёт заказов печати —
  это новый инфоблок по образцу orders.
- Живьём не проверено: на машине разработки нет ядра и лицензии Битрикса,
  поэтому реальная запись, CAPTCHA и отправка письма не выполнялись
  (docs/bitrix-integration.md:354-356).

================================================================
4. ЧТО НУЖНО, ЧТОБЫ «ЗАКАЗАТЬ» ЗАРАБОТАЛО ПО-НАСТОЯЩЕМУ
================================================================

1. PHP 8.0+ и MySQL (Laragon есть) + установленный Битрикс «Старт» и выше.
2. Развернуть шаблон в local/, выполнить миграции из db/ (создадут
   9 инфоблоков, включая bookings / orders, и почтовое событие).
3. В админке: «Настройки -> Настройки продукта -> Почтовые события ->
   Почтовые шаблоны -> NLB_NEW_REQUEST» — вписать реальный ящик.
4. Проверить, что CAPTCHA включена и сессии работают (иначе sessid
   не совпадёт и форма вернёт ошибку).
