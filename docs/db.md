# База данных: инфоблоки, свойства, контент

Документ описывает слой данных, который создают миграции `db/`. Это источник
правды для шаблонов компонентов: коды инфоблоков, коды свойств и XML_ID
значений списков должны совпадать с тем, что написано здесь.

Установка и запуск миграций — `../db/README.md`. Здесь — модель данных.

---

## 1. Зачем отдельный слой

Шаблон `nlb_bootstrap` — оформление. Данные приходят из инфоблоков Битрикса:

```
db/config/iblocks.php      структура: типы, инфоблоки, свойства, разделы
db/config/data/*.php       демо-контент: элементы с датами и свойствами
db/migrations/*.php        создание структуры через API Битрикса
        │
        ▼
   MySQL (b_iblock*, b_iblock_element*)
        │
        ▼
bitrix:news.list / news.detail  → шаблоны news_cards, events_cards, article
```

Коды, а не ID: на каждой установке ID свои, коды одинаковые. Поэтому в
вызовах компонентов используется `IBLOCK_ID` из поиска по `CODE`
(см. § 7), а не число из демо-базы.

## 2. Типы инфоблоков

| ID | Название | Разделы | Для чего |
|---|---|---|---|
| `nlb_content` | Контент библиотеки | да | новости, события, подарочные наборы |
| `nlb_catalog` | Каталог продукции | да | сувениры и мерч |
| `nlb_services` | Услуги библиотеки | нет | услуги и печать |

Свои типы, а не демо-тип `news`: при обновлении демо-данных Битрикса
(`/bitrix/modules/*/install`) чужие типы не затрагиваются, а свои — тем более.

## 3. Инфоблоки

| Код | Название | Тип | Список | Детальная | Раздел |
|---|---|---|---|---|---|
| `news` | Новости | `nlb_content` | `/news/` | `/news/#ELEMENT_CODE#/` | `/news/#SECTION_CODE#/` |
| `events` | События | `nlb_content` | `/events/` | `/events/#ELEMENT_CODE#/` | `/events/#SECTION_CODE#/` |
| `collections` | Подарочные наборы | `nlb_content` | `/collections/` | `/collections/#ELEMENT_CODE#/` | — |
| `books` | Сувенирная продукция | `nlb_catalog` | `/books/` | `/books/#ELEMENT_CODE#/` | `/books/#SECTION_CODE#/` |
| `services` | Услуги | `nlb_services` | `/services/` | `/services/#ELEMENT_CODE#/` | — |
| `printing` | Печатные услуги | `nlb_services` | `/printing/` | `/printing/#ELEMENT_CODE#/` | — |
| `requests` | Обращения | `nlb_content` | `/feedback/` | — | — |
| `bookings` | Заявки на услуги | `nlb_content` | `/services/` | — | — |
| `orders` | Заказы сувениров | `nlb_content` | `/books/` | — | — |

Общие настройки всех инфоблоков:

- `ACTIVE = Y`, `VERSION = 2` (свойства в отдельной таблице);
- права: группа 2 «Все пользователи» — `R` (чтение), иначе гости увидят пусто;
- `INDEX_ELEMENT = Y` — элементы участвуют в поиске;
- символьный код обязателен, транслитерация включена.

Исключение — три инфоблока заявок (`requests`, `bookings`, `orders`). Это
рабочая база, а не контент:

- `INDEX_ELEMENT = N` — персональные данные не должны попадать в поиск;
- группа 2 получает `W` (запись), иначе анонимная форма не создаст элемент;
- файлов демо-данных у них нет: пустой инфоблок — нормальное состояние.

|---|---|---|---|
| `ITEM` | Товар | строка | название на момент заказа |

| `PERSON` | Имя заказчика | строка | обязательное |
| `PHONE` | Телефон | строка | обязательное |
| `EMAIL` | E-mail | строка | |
| `COMMENT` | Комментарий | строка | |
| `STATUS` | Статус | список | `new` / `processing` / `done` / `cancelled` |
| `SOURCE` | Источник | строка | канал: `utm:telegram`, `ref:t.me`, `site`, `direct` |
| `CREATED_BY` | Ответственный | строка | логин или ID закрывшего, не имя |
| `DATE_PROCESSED` | Дата обработки | строка + `DateTime` | `дд.мм.гггг чч:мм:сс` |

Три последних свойства есть у всех трёх инфоблоков, но их не передаёт форма —
их пишут обработчики в `nlb_forms.php`:

- **`SOURCE`** — `OnBeforeIBlockElementAdd` вызывает `nlb_form_source_value()`:
  `utm_source`, затем `utm_medium` → `utm:<slug>`; внешний `HTTP_REFERER` →
  `ref:<host>`; свой домен (и `localhost`) → `site`; ничего не пришло →
  `direct`. Slug собирается из `[a-z0-9._-]` и обрезается до 40 символов,
  поэтому в базе нет длинных ссылок с параметрами. Скрытое поле в форме не
  нужно: значение читается из запроса на сервере.
- **`DATE_PROCESSED` и `CREATED_BY`** — `OnAfterIBlockElementUpdate`. Закрытые
  статусы: `request` → `done`; `booking` → `confirmed`, `cancelled`; `order` →
  `done`, `cancelled`. При закрытии ставится дата (если она ещё пуста) и
  ответственный (если пуст): логин `$USER`, а если логина нет — его ID.
  Возврат в открытый статус очищает `DATE_PROCESSED`, чтобы «висит без
  ответа» считалось по текущему состоянию, а не по истории правок.

Колонки списка заявок в админке задаёт `013_request_source.php` через
`CGridOptions::SetDefaultView()` (grid `tbl_iblock_list_` + md5 от
`<тип>.<ID>`): `ID`, `NAME`, `STATUS`, `SOURCE`, `CREATED_BY`,
`DATE_PROCESSED`, `TIMESTAMP_X`. Свойства в списке по умолчанию не видны, а
без них аналитика остаётся в базе, но не на экране. `SetDefaultView()` пишет
`main.interface.grid.common` и применяется, только если у сотрудника нет своей
сохранённой вьюхи; иначе — «Настроить список → По умолчанию».

Серверные проверки — обработчики `OnBeforeIBlockElementAdd` в
`local/php_interface/include/nlb_forms.php`: согласие на обработку данных,
дата не в прошлом, занятый слот. Проверка слота не зависит от JavaScript:
`nlb_form_slot_taken()` ищет активные брони с тем же `SERVICE_CODE`, `DATE`
и `TIME` (отменённые не считаются).

## 5. Списки значений (XML_ID)

XML_ID — стабильный ключ значения. В конфиге демо-контента указывается
именно он, миграция переводит его в числовой ID.

| Свойство | XML_ID → значение |
|---|---|
| `news.TAGS` | `books` Книги, `digital` Цифровые ресурсы, `events` События, `kids` Дети, `science` Наука, `library` Библиотека |
| `events.CATEGORY` | `literature` Литература, `children` Для детей, `tech` Технологии, `lecture` Лекции |
| `events.FORMAT` | `offline` Офлайн, `online` Онлайн, `hybrid` Гибрид |
| `books.AGE_LIMIT` | `all` Всем, `kids` Детям, `adult` Взрослым |
| `books.AVAILABLE` | `available` В наличии, `reserved` Под заказ, `unavailable` Нет в наличии |
| `requests.STATUS` | `new` Новое, `in_progress` В работе, `done` Обработано |
| `bookings.STATUS` | `new` Новая, `confirmed` Подтверждена, `cancelled` Отменена |
| `orders.STATUS` | `new` Новый, `processing` В работе, `done` Выполнен, `cancelled` Отменён |
| `*.COLOR` | `primary` Синий, `green` Зелёный, `sky` Голубой, `pink` Розовый, `orange` Оранжевый |

Цвет в шаблоне превращается в класс: `primary` → `icon-tile--primary`,
`collection-card--primary`, `bg-grad-primary`.

## 7. Как страницы получают данные

В коде страницы не должно быть чисел вроде `'IBLOCK_ID' => 2`: на другой
установке это будет другой инфоблок. Используйте поиск по коду.

### 7.1. Готовый помощник

`db/lib/helpers.php` содержит `nlb_iblock_id('news')`, но подключать его на
каждой странице не нужно. Для продакшена удобнее один раз создать
`local/php_interface/include/nlb_db.php`:

```php
<?php
if (!defined('B_PROLOG_INCLUDED') || B_PROLOG_INCLUDED !== true) {
    die();
}

function nlb_iblock_id(string $code): int
{
    static $cache = [];
    if (isset($cache[$code])) {
        return $cache[$code];
    }
    $id = 0;
    $res = CIBlock::GetList([], ['CODE' => $code, 'CHECK_PERMISSIONS' => 'N']);
    if ($row = $res->Fetch()) {
        $id = (int)$row['ID'];
    }
    return $cache[$code] = $id;
}
```

и подключить его в `local/php_interface/init.php`:

```php
require_once __DIR__ . '/include/nlb_db.php';
```

### 7.2. Вызов компонента

```php
$APPLICATION->IncludeComponent('bitrix:news.list', 'news_cards', [
    'IBLOCK_TYPE' => 'nlb_content',
    'IBLOCK_ID' => nlb_iblock_id('news'),
    'NEWS_COUNT' => 4,
    'SORT_BY1' => 'ACTIVE_FROM',
    'SORT_ORDER1' => 'DESC',
    'FIELD_CODE' => ['NAME', 'PREVIEW_TEXT', 'PREVIEW_PICTURE', 'ACTIVE_FROM', 'DETAIL_PAGE_URL'],
    'PROPERTY_CODE' => ['AUTHOR', 'TAGS', 'READ_TIME'],
    'CHECK_DATES' => 'Y',
    'SET_TITLE' => 'N',
    'CACHE_TYPE' => 'A',
    'CACHE_TIME' => 3600,
], false, ['HIDE_ICONS' => 'Y']);
```

Полные примеры для каждой страницы — `bitrix-integration.md`, § 3–12.
Шаблоны компонентов (`news_cards`, `events_cards`, `books_cards`, `article`,
`event`) — в `../local/templates/nlb_bootstrap/components/bitrix/`.

### 7.3. Количество вместо счётчиков

Отдельных счётчиков (просмотры, заказы, «сколько раз воспользовались»)
в структуре нет. На сайте показывается только **количество активных
элементов**:

```php
nlb_iblock_count('services');  // 8 из демо-набора
nlb_counts();                  // все шесть инфоблоков сразу
```

`nlb_iblock_count()` кеширует результат на время запроса и не тянет строки:
используется `SelectedRowsCount()` результата `CIBlockElement::GetList`.
Для больших каталогов этого достаточно; отдельный модуль статистики не нужен.

Если понадобится именно счётчик просмотров — это новая задача (модуль
«Статистика» или внешняя аналитика), а не поле в инфоблоке.

| `printing` | 37 | с 1 сентября 2026 | `print-*.jpg` (8 фото, остальные — заглушка) |

У `requests`, `bookings`, `orders` демо-элементов нет: это рабочая база
заявок, она наполняется с сайта. `check.php` не считает их отсутствие
ошибкой (флаг `user_data` в конфиге).

Тексты, цены, артикулы, телефоны и адреса — **демонстрационные**. Перед
публикацией их нужно заменить (бэклог, P0-9). Даты событий специально в
будущем относительно даты поставки: афиша должна выглядеть живой.

Картинки лежат в `assets/images/` шаблона; миграция копирует их в
`upload/` через `CFile::MakeFileArray`, поэтому после установки они
принадлежат сайту и не зависят от файлов шаблона.

### 8.1 Индекс поиска (`db/search/`)

Каталог `db/search/` — не база, а производный артефакт: `pages.json`
(8 курируемых страниц: контакты, часы, запись на событие, афиша, сувениры,
каталог, услуги, обратная связь) и `index.json`, который из него и из
`db/config/data/*.php` собирает `php tools/build-search-index.php`.

Правится вручную только `pages.json`; `index.json` руками не трогают —
`db/lint.php` его не проверяет, а свежесть сверяет `--check` по пофайловым
sha256 источников. После любой правки данных, конфига инфоблоков или
страниц индекс пересобирают, иначе поиск отдаёт старые заголовки и ссылки.

На живом ядре те же документы берутся из инфоблоков
(`nlb_search_documents_from_bitrix()`), поэтому команда сборки не меняется;
`pages.json` остаётся нужен — этих текстов (часы, «как записаться») в
инфоблоках нет.

## 9. Проверки и изменения

```bash
php db/lint.php      # конфиги без Битрикса: коды, XML_ID, даты, картинки, иконки
php db/run.php       # применить
php db/check.php     # сверить базу с конфигами
php db/tests/run.php # прогон миграций на заглушках ядра (37 проверок)
```

Добавить свойство:

1. описать в `db/config/iblocks.php` → `properties`;
2. `php db/lint.php` → `php db/run.php --only=003`;
3. добавить код в `PROPERTY_CODE` вызова компонента;
4. очистить кеш.

Добавить элемент: `db/config/data/<инфоблок>.php` с новым уникальным
`xml_id` → `php db/run.php --only=005`. Новые элементы создаются, а
существующие демо-элементы с `XML_ID` на `nlb-` обновляет шаг 010 —
он же снимает старые книжные обложки и чистит поля, которых больше нет
в конфиге. Элементы, созданные в админке, миграции не перетирают.

Уже работающая установка получает инфоблоки заявок и почтовое событие
`NLB_NEW_REQUEST` отдельным шагом:

```bash
php db/run.php --only=008
```

Шаг идемпотентный: существующие инфоблоки, свойства и шаблон письма он не
дублирует.

Книжную базу переводят на сувениры два идемпотентных шага:

```bash
php db/run.php --only=009   # названия и адреса инфоблоков
php db/run.php --only=010   # свойства, разделы, элементы
```

009 обновляет `NAME`, `SORT` и URL списков/деталей/разделов у шести
контентных инфоблоков. 010 переименовывает свойства (`AUTHOR` → «Материал»,
`YEAR` → «Размер», тип `YEAR` — строка), добавляет `PRICE`, переименовывает
разделы, заменяет книжные элементы 24 сувенирами, шесть коллекций —
подарочными наборами, дополняет печать до 37 позиций, исправляет `UNIT`
и заменяет шесть услуг восемью премиальными с новыми свойствами. Оба шага
сравнивают поля с текущими значениями, поэтому повторный запуск даёт
`изменено: 0`.

## 10. Ограничения

- **Не проверено на реальном ядре.** Ядра Битрикса на машине разработки нет
  (см. `Что доделать.txt`, P0-11). Логика миграций прогнана на заглушках
  (`db/tests`), синтаксис — `php -l`, структура — `db/lint.php`. Отдельно
  не проверен прогон 009/010 на уже заполненной базе: обновление свойств
  версии 2, смена типа `YEAR` и удаление старых обложек через API.
- Счётчиков услуг/просмотров нет: выводится только количество элементов
  (§ 7.3). Если нужна статистика — отдельная задача.
- Версия свойств — 2. При переводе существующего инфоблока с версии 1
  свойства переносятся ядром отдельной операцией.
- Демо-контент не претендует на библиографическую точность.
- Поисковый индекс после миграций нужно перестроить вручную
  (**Поиск → Переиндексация**).
